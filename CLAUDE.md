# Life RPG — iOS app

Personal-use life RPG app, single-user, not published to the App Store. Full design in `doc/PLAN.md`; the library a fresh install starts from is `doc/starter_library.json`.

## Structure

- `LifeRPGCore/` — Swift Package holding models, rules, sampling and settlement logic. No UIKit/SwiftUI dependency, runnable directly with `swift test`
- `LifeRPG/` — Xcode app target: SwiftUI views, HealthKit / EventKit integration, import/export only
- `doc/` — PLAN.md, DEV_PLAN.md, and `starter_library.json`

Keep as much logic as possible in Core; views should only render. When working in Core you (Claude) only need the `swift` commands, not `xcodebuild`.

**Current status: the daily journal is one document per day (device checks open: the V8 store upgrade, the Shortcut hand-off, the App Intent, Foundation Models on the phone). `JournalEntry` (`SchemaV8`, now `SchemaV10` — V9 added `isArchived` and V10 the optional `starterKey` to both library models; `blocksJSON` of `JournalBlock`s, each `Text` or `Prompt` with a `source` of llm or fixed and a `fixedKey`; `doneAt` is only a cosmetic status; the word count is derived, never cached; export `schemaVersion` 10 — the whole library included, each row with its `starterKey` —, import reads 3–10) holds a day. `JournalDocument` is the pure editing rules (insert a prompt at the cursor and split the text, return at the end of an answer, backspace on an empty answer, remove a question, merge adjacent texts); `JournalEntries.save` normalizes and deletes an entry that holds only whitespace. The old two-mode journal's `JournalTurn` rows are kept and never deleted; `JournalMigration.migrateTurns` copies them into entries ONCE (the app guards it with the `journalTurnsMigrated` flag, because a day the user cleared looks exactly like an unmigrated one). The editor (`LifeRPG/Journal/`) is one `UITextView` per block (the app supports iOS 17.6, which has no SwiftUI cursor API) with a chip bar and a 500 ms autosave. The journal's day is the app day, which ends at 05:00. Nothing is sent while the user can still edit: Apple Journal's Shortcuts can only create an entry, never change one, so the user's Shortcut (`Get Journal Text to Send`, then Create Journal Entry) runs from a Personal Automation at 05:00 and `JournalSend.finishedDayKey` / `textToSend` give it the day that has just ended, once (`JournalSentLog` in UserDefaults records the fingerprint; the reader says when a day was sent and whether it was edited since). The calendar pencil (`JournalMarks`, fixed bands under 100, 100 to 299 and 300+ words), the day sheet's night card, the reader and the Trends tab (`TrendsView` from one `TrendsPage` value in Core, locked until 7 days have an entry) all read entries. `Ask me something` (the pill in the editor's bar; Core `JournalAsk`: request, accept, resolve with a 6 second timeout and the fixed fallback order, a cap of 5 llm prompts, a safety line instead of a model call when the writing holds a `JournalSafety` keyword; the Settings toggle `journalSendWriting` decides whether the entry text is sent) is built, and so are the calendar and day sheet redesign and the all-entries list with search; the spec is `Downloads/LifeRPG Journal UX logic spec.md`. Nothing about the on-device model's wording quality is verified. 1291 Core tests (the counts below are older). A name the person gives the app (asked once on first launch, changeable in Settings; `UserDefaults` only, so not in a backup; `UserProfile.cleanName`, shown in the greeting) and Settings → Data → `Erase all records…` (`EraseRecords`: deletes every history table and the journal, keeps the library with the user's edits, resets what the history wrote onto it, and the app then gives the opening balance again) are built. Local reminders (`NotificationPlan` in Core: an evening one at 20:00 unless today is written, a morning one naming the routines due; the app's `NotificationService` rebuilds the queue whenever the app comes forward or goes away, which is how writing cancels tonight's) and an in-app way to add rows a newer starter library gained (`StarterUpdate`, offered from a card at the top of the Library) are built. `tier` comes from `Energy.inputs` (HealthKit via `HealthService`) and is fixed when the day is generated, but body data is re-read on every foreground: when it disagrees, `Replan` offers to re-plan **only what is still open** — finished work is never touched. Cycle days 1–3 are capped at tier `low`, which is the only cycle rule there is. Auto-verify evidence is passed to `ensureToday` as `[dayKey: DayEvidence]`. Routine load is **not** an input — `ensureToday` schedules the day's routines and counts them itself.

`LifeRPGCore` is a single library target + `LifeRPGCoreTests` (Swift Testing, Swift 5 language mode). `LifeRPG.xcodeproj` (target/scheme `LifeRPG`, iOS 17.6+, iPhone only) links the local package; `LifeRPG/` is a synchronized folder, so new files placed there are picked up without touching `project.pbxproj`. `@Model` requires full Xcode as the active developer dir (Command Line Tools lack the SwiftData macro plugin).

Starter library: `doc/starter_library.json` (general quests and routines, no personal content) is only an initial draft. `LifeRPG/Seed/starter_library.json` is a symlink to it (Xcode copies the real file into the bundle). Core's `StarterLibrary` decodes and validates it (schedules the calendar can read, reachable weekly targets, lighter versions that point at real routines, no epic claiming hidden / weekend) and `StarterLibrary.install` inserts it **once**, into a store whose library tables are both empty (through `SeedImporter.seedIfEmpty`); a store with any row is never touched, so a row added to the file later does not arrive and a row the user renamed or deleted can't come back. The original author's CSVs now live only as test fixtures (`LifeRPGCore/Tests/LifeRPGCoreTests/Fixtures/*.csv`, parsed by the test target's `SeedParser`); most Core tests run against them, and `StarterLibraryTests` is what keeps the shipped file honest. `starterKey` is the stable key the file gives each row, stamped on install and on add; `StarterUpdate.claim` stamps older rows by their words once, and a row that carries a key (renamed or archived included) is never offered again. The library in the DB is the source of truth: rows are identified by id, renamed in place, and deleted by archiving (`isArchived`, unlisted and inactive, restorable from the Library's Archived section). The backup carries the whole library (`fullLibrary`, schema 10).

## Commands

- Build the logic layer: `swift build --package-path LifeRPGCore`
- Run tests: `swift test --package-path LifeRPGCore`
- Build the app (no simulator launch): `xcodebuild -scheme LifeRPG -destination 'platform=iOS Simulator,name=iPhone 17 Pro Max' build`

## Rules

- **Never hand-edit `LifeRPG.xcodeproj/project.pbxproj`.** When a new file is needed, create it in the right directory and tell me to confirm it in Xcode — don't edit the project file yourself.
- Before changing an `@Model` definition, explain the impact on existing data. SwiftData's automatic migration only handles simple cases like adding fields; renaming or changing a type needs a migration plan.
- CloudKit-ready constraints: every `@Model` property must have a default value or be optional, no `@Attribute(.unique)`, all relationships optional. Breaking this will blow up later when CloudKit is turned on.
- Balance is always derived by summing `LedgerEntry`; never add a cached balance field.
- **One metric for one thing.** `intensity` was removed because difficulty already graded how hard a thing is; don't reintroduce a second axis for "how demanding". A routine's lighter version is a `RoutineTask` row with its own points and rule, not a text field.
- Quest text is snapshotted on the instance — never turn history records into references back to the template. `DailyQuest` **is** the per-day history the calendar and summary read: never overwrite a row to save adding one.
- `QuestRating` / `QuestComment` are append-only and dated. A changed opinion is a new row, never an overwrite — "what have I been rating highest lately" only works while the old rows survive.
- **A rule lives in exactly one place, in Core.** A view that needs one passes in the rows its `@Query` already holds (`Streak.completedDayKeys(_:)`, `Economy.balance(_:)`, `Economy.totalEarned(_:)`) rather than re-filtering or re-summing beside the HUD. This has already drifted twice; if a rule needs a `[Model]` overload to make that possible, add the overload.
- Anything derived from an already-awarded value takes that value as a parameter and never recomputes it — `Scoring.breakdown(_:tier:awarded:)` has no RNG in its signature on purpose, so the reveal animation physically cannot re-roll the points it is displaying.
- Dates always use `dayKey` (`"2026-09-17"`, local timezone) and `weekKey` (`"2026-W38"`) strings; never compare `Date` directly in business logic.
- Write tests in Core before new logic. Where `PLAN.md` states expected numbers (the reroll ladders, the penalty worked example), assert those literals rather than recomputing them with the formula under test.
- Never put credentials like the Oura token in code or tests — tokens go through Keychain.
